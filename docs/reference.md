# 参考文档：设计原则 / 模板 / 脚本 / 记忆原则

---

## 核心设计原则（来自 AI 原生工程实践）

### 原则一：AI 看不见的东西等于不存在
凡是没有写入文件的内容，对 AI 来说就是不存在的。所有架构决策、业务规则、技术约定、纠偏记录，**必须落地为 `ai-dev-workflow/` 下的文件**。

### 原则二：地图优于手册
BOOTSTRAP.md 是地图（目录），不是百科全书，保持在 100 行以内。上下文是稀缺资源：信息塞得越多，AI 对关键约束的感知反而越弱。

### 原则三：渐进式披露
AI 从最小稳定入口（BOOTSTRAP.md）出发，按需深入。不要在 BOOTSTRAP.md 中堆砌细节，细节应在恰当的深度文件里。

### 原则四：品味约束，而非实现微管理
关心**边界、正确性、可维护性**，不关心具体实现风格。把团队偏好编码为明确规则（写入 DECISIONS.md 或 TWEAKS.md），而不是每次口头重申。

### 原则五：持续还债，而非集中清理
AI 会复制已有模式——包括坏模式，技术债会自我繁殖。**小增量持续清理 >> 痛苦的周期性大重构。**

## 人与 AI 的职责边界

> 来自 OpenAI Harness Engineering 实践：当 AI 承担大量代码工作后，人的职责发生了根本性转变。

**人负责**：
- 优先级判断（做什么 / 不做什么）
- 把用户反馈翻译成可验收的具体标准
- 验证结果（是否达成了目标）
- 识别"Agent 遇到困难"= 环境缺失了什么

**AI 负责**：
- 实现、测试、文档
- 记录变更、更新工作流文件
- 在遇到障碍时诊断缺失并写出修复

> **核心转变**：人不再写代码，而是设计 Agent 工作的环境（工具、约定、文档、反馈回路）。

## AGENTS.md 模式（可选）

部分 AI 编码工具（如 OpenAI Codex、Cursor）会识别仓库根目录的 `AGENTS.md` 文件，将其作为对 Agent 行为的专项指令。

**与本工作流的关系**：

| 文件 | 角色 |
|---|---|
| `ai-dev-workflow/BOOTSTRAP.md` | 导航地图：让 AI 知道去哪里找信息 |
| `ai-memory/context/TWEAKS.md` | 行为纠偏：硬约束规则 |
| `ai-memory/context/DECISIONS.md` | Golden Principles + 架构决策 |
| 仓库根目录 `AGENTS.md`（可选）| 工具级行为指令（部分工具专用）|

如果你使用 Codex 或 Cursor，可以在仓库根目录创建 `AGENTS.md`，内容从 BOOTSTRAP.md 导航 + TWEAKS.md 最重要的几条规则中提炼，保持在 50 行以内。

## Golden Principles（黄金原则）

> 区别于一般技术决策：Golden Principles 是**机械的、可强制执行的、每行代码都要遵守**的规则。

在 `DECISIONS.md` 顶部维护一个 `## Golden Principles` 专区，放入此类规则，例如：
- 共享工具方法优于各模块手写重复逻辑
- 接口参数边界必须校验，不允许 YOLO 式直接使用
- 所有外部依赖版本必须固定，不使用浮动范围

**特征**：
- 简短且可操作（一句话，不需要解释）
- AI 可以自动发现违反的地方
- 人类审查时 5 秒以内即可判断是否合规

在每次代码审查或变更中，AI 应主动检查是否违反了 Golden Principles。

## CURRENT_TASK.md 模板

```markdown
# 当前任务

**项目**: {项目名}
**当前需求**: {需求名 / 修复描述}
**状态**: 进行中 / 阻塞 / 已完成
**执行计划**: 见 demand/exec-plans/active/{文件名}（如有）

## 进度

- [ ] 子需求 1
- [x] 子需求 2（已完成）
- [ ] 子需求 3

## 断点快照（上次停在哪里）

> 每次会话结束或中断时更新此区域，让下次新会话可以精确续接。

**最后修改的文件**：{完整路径}
**做到一半的事**：{描述，如"已完成接口定义，正在写实现，controller 还没关联"}
**未验证的变更**：{是否有代码改好了但没跑测试/没手动验证}

## 阻塞问题

> 无 / 列出当前卡点

## 下一步

1. {具体要做的第一件事}
2. {第二件事}

## 备注

{其他上下文}
```

## 模块文档最小模板（modules/{module-name}.md）

```markdown
# 模块：{module-name}

**最近更新**: YYYY-MM-DD

## 1. 职责与边界
- 负责：（此模块解决什么问题）
- 不负责：（明确边界，避免越界）

## 2. 输入与输出
- 输入：请求 / 事件 / 上游依赖
- 输出：响应 / 事件 / 下游影响
- 关键数据结构/字段（仅列核心）

## 3. 关键流程（Happy Path）
1. 步骤 A
2. 步骤 B

## 4. 异常与降级
- 失败场景及兜底策略（重试/降级/告警）

## 5. 依赖关系
- 内部依赖模块
- 外部依赖（数据库/API/消息系统），详见 `resources/`

## 6. 关键约束
- 幂等性 / 一致性 / 权限 / 性能 / SLA 等硬约束

## 7. 最近变更影响
- 本次改动点：
- 影响范围：
- 回滚关注点：
```

## 跨会话记忆原则：已探索过的目录结构、模块关系，写入 `ARCHITECTURE.md`
2. **不要重复犯错**：每次被纠正，立即写 `TWEAKS.md`
3. **文档同步代码**：文档与代码不一致比没有文档更危险
4. **定期归档**：`records/` 中超过 3 个月且已上线的记录归档至 `records/archive/`
5. **保持精简**：CURRENT_TASK.md 只保留当前任务；BOOTSTRAP.md 始终 ≤100 行

## 熵管理：持续小清理 + 主动扫描

**被动触发（发现即修）**：
- 同类逻辑在多处重复实现
- 文档描述与实际代码不符
- TWEAKS.md 中同一类错误出现 ≥3 次
- 某模块每次都需要重新探索（modules/*.md 缺失或过时）

**主动扫描（定期触发，推荐每周或每 Sprint）**：
- 扫描是否有违反 DECISIONS.md Golden Principles 的代码
- 检查 TWEAKS.md 是否有 ≥3 次的同类纠偏未提炼为原则
- 检查 ARCHITECTURE.md 是否与实际目录结构一致
- 审视近期是否出现了 BOOTSTRAP.md 中未描述的新模块

**处理方式**：
- 立即在当前任务中顺手修复
- 修复后更新对应文档
- 重复模式提炼为 DECISIONS.md Golden Principles 规则

> 技术债就像高息贷款：持续小额还款远优于积累后的痛苦大清算。人类的品味只需捕获一次，之后在每行代码上持续强制执行。
