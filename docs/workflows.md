# 开发工作流 — 执行指令

> 实现需求 / 修复 / 重构时读此文件。

---

## 4.1 正式需求实现流程

1. 读 `ai-dev-workflow/demand/` 中对应的需求文档
2. 需求涉及外部服务（数据库/API/第三方）时，先读 `resources/` 下的相关文档，获取连接信息和接口规范，再开始实现
3. 判断需求复杂度：
   - 1-3 个子任务，半天内可完成 → 直接用 CURRENT_TASK.md 跟踪
   - 多子任务 / 跨多天 / 涉及多模块 → 先创建执行计划（见 4.2），再开始实现
4. 按子需求逐步实施，**每完成一个子需求后立即执行**：
   - 勾选 `CURRENT_TASK.md` 进度
   - 在 `ai-memory/changed/CHANGELOG.md` 追加一行摘要
   - 在 `ai-memory/changed/records/` 创建变更记录文件
   - 发现可复用规则或技术决策 → 追加到 `DECISIONS.md`
   - 变更涉及架构 → 同步更新 `ARCHITECTURE.md`
5. 全部子需求完成后：
   - 更新 `CURRENT_TASK.md` 状态为"已完成"
   - 需求文档移至 `demand/done/`
   - 执行计划从 `exec-plans/active/` 移至 `exec-plans/completed/`

## 4.2 复杂需求执行计划（Exec Plan）

在 `demand/exec-plans/active/YYYY-MM-DD_{需求名}.md` 创建：

```markdown
# 执行计划：{需求名}

**关联需求**: demand/{需求文档文件}
**创建时间**: YYYY-MM-DD
**预期完成**: YYYY-MM-DD

## 子任务清单

- [ ] 子任务 1：{描述} — 涉及文件：{完整路径}
- [ ] 子任务 2：{描述}
- [x] 子任务 3：{描述}（完成于 YYYY-MM-DD）

## 进度检查点

### YYYY-MM-DD
完成了：
发现了：
下一步：

## 决策日志

### D1 | {决策简述} — YYYY-MM-DD
背景：
方案：A / B / C
选择：A
原因：
```

## 4.3 临时修复 / 优化 / 问题排查

完成代码变更后立即执行（不需要创建需求文档）：

1. 更新 `CURRENT_TASK.md`：当前需求改为简短描述，状态改为"已完成"
2. 在 `CHANGELOG.md` 追加一行摘要
3. 在 `records/YYYY-MM-DD_{简短描述}.md` 创建变更记录：问题描述、根因、修改的文件、验证方式
4. 变更揭示了新架构约定 → 追加到 `DECISIONS.md`

---

## 4.4 文档编写硬规则

- 代码引用**必须**使用完整限定路径（后端：`com.example.service.impl.XxxServiceImpl`；前端：`src/views/xxx/components/XxxDialog.vue`）
- 变更记录摘要不超过 80 字；超出部分移至 records/ 文件
- BOOTSTRAP.md 严格保持 ≤100 行；超出时立即删减，不得放宽

---

## 4.5 新增需求

1. 创建 `demand/{YYYY-MM-DD}_{简短描述}.md`，包含：需求背景与目标、功能点拆解（子需求列表）、涉及模块/文件、验收标准
2. 更新 `CURRENT_TASK.md`：替换需求名，重置进度列表，清空阻塞问题
3. 旧需求未完成时：在旧 `CURRENT_TASK.md` 中标记"暂停"，不得直接覆盖

---

## 4.6 已交付需求变更

1. 在 `demand/done/` 找原需求文档，在 `ai-memory/changed/records/` 找原变更记录
2. 创建 `demand/{YYYY-MM-DD}_{原需求名}_变更.md`，包含：关联原需求路径、变更内容、影响范围分析
3. 更新 `CURRENT_TASK.md`（同 4.5 步骤 2）
4. 完成后按变更大小处理原文档：
   - 小调整（文案/边界 bug）→ 变更说明追加到原文档末尾
   - 功能变更/新增 → 原文档移至 `demand/done/archive/`，新变更文档归档至 `demand/done/`

---

## 4.7 遇到困难时的标准协议

**触发场景**（命中任一条执行此协议，不得重试）：
- 找不到某个接口 / 方法 / 文件
- 不确定某个规则或约定
- 连续两次尝试都失败
- 需要猜测业务逻辑才能继续

**执行步骤**：

1. 诊断缺失：问自己"如果这个信息已经写在某个文档里，我就不会卡住——应该写在哪里？"
2. 立即写入对应文件：
   - 规则/约定缺失 → 写入 `DECISIONS.md` 或 `TWEAKS.md`
   - 接口/模块缺失 → 在 `ai-memory/structure/modules/` 下补充文档
   - 外部服务信息缺失 → 写入 `resources/` 对应文件
   - 架构信息缺失 → 补充 `ARCHITECTURE.md`
3. 环境补全后，继续实现

**不确定但非阻塞**：用 `// TODO (AI) <原因> -- YYYY-MM-DD` 标记，任务完成后统一处理

**需要用户澄清**：暂停实现，提问，获得答案后将答案写进文档，不得留在对话中

---

## 4.8 模块文档（modules/*.md）硬触发规则

**触发新增**（命中任一条必须创建新文件）：
1. 新增业务模块/子域
2. 模块职责或边界调整（包括澄清）
3. 跨模块数据流或调用链变化

**触发更新**（命中任一条必须更新已有文件）：
4. 关键约束变化（幂等、一致性、缓存、降级、权限、SLA）
5. 同一模块在 14 天内被"临时重新探索" ≥2 次
6. 新增或删除 `modules/*.md` 文件时，必须同步更新 `ARCHITECTURE.md` 的「模块索引」表

**执行要求**：
- 代码变更与模块文档更新必须在同一轮完成
- 局部变更也要更新"最近更新"时间和"最近变更影响"段落
- **未完成模块文档更新，不得标记该子任务为完成**
- 模块文档模板见本 skill 的 `docs/reference.md`
